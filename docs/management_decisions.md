# 경영 판단 지표 추가 · 2026-10-06

## 적용 범위

기존 대시보드에 경영 판단 카드를 추가한다. 기존 조회 결과를 재사용하며 원본 금액, DB 스키마, 캐시 무효화 경로, 워커·스레드 설정, 독립 계산기는 변경하지 않는다.

- 수익 변화: 전월 비교 기간 대비 조제료·일매순익·비보험 차액·잡이익의 증감.
- 잡이익 포함·제외 실적: 잡이익을 일회성으로 추정하거나 분류하지 않는다.
- 영업일수와 하루 실적 효과: 두 기간에 입력 누락·휴무 설정 불일치·날짜별 합계 불일치가 없을 때만 계산한다.
- 분석 근거: 지정 영업일수, 실제 입력일수, 과거 미입력일, 오늘 마감 대기, 미래 입력 제외, 예측 표본 수.
- 월 목표: 전체 또는 잡이익 제외 실적을 기준으로 필요한 하루 평균을 브라우저에서 계산한다. 목표는 사용자·월별로 해당 브라우저에만 저장한다. 입력 누락·설정 불일치·합계 불일치가 있으면 목표 계산을 보류한다.
- 운영 CSV: 기존 열 뒤에 입력일수, 잡이익 제외 합계, 집계 기준을 추가한다. CSV는 저장된 월 전체를 내보내며 화면의 기준일 누적과 구분한다.

## 계산과 데이터 경계

진행 중인 달은 전월의 같은 일자까지 비교하며 짧은 달은 말일로 제한한다. 완료된 달은 전월 전체와 비교한다. 미래 기록은 분석에서 제외한다. 0원 입력도 영업 기록으로 포함한다.

공식 분석 합계는 일별 total과 기간 내 잡이익의 합이다. 세 수익 항목과 total의 차액은 별도 표시하며 잡이익으로 편입하지 않는다. 서로 다른 날짜의 차액이 상쇄되어도 일별 일치로 판정하지 않는다.

영업일수 효과 = 전월 하루 평균 × 영업일수 차이. 하루 평균 효과 = 잡이익 제외 합계 증감 − 영업일수 효과. 원 단위 반올림 후 두 효과가 실제 증감에 일치하도록 계산한다. 이는 산술적 분해이며 요일 구성·휴일·영업시간의 인과관계를 확정하지 않는다. 과거 영업일도 현재의 영업 설정을 적용한다.

## 성능 유지 방식

새 DB 연결·조회, 외부 API, 외부 라이브러리, DB 조인, 백그라운드 작업을 추가하지 않는다. 기존 주차별 잡이익 조회를 비교 기간과 공유한다. 겹치는 기간은 하나의 날짜 범위로, 떨어진 기간은 UNION ALL로 조회하여 각 범위에서 기존 (user_id, date) 인덱스를 사용한다. 모든 조회는 기존 사용자 범위를 유지한다.

목표 계산에는 약 4KB의 바닐라 JS 정적 파일 하나를 사용한다. 화면의 기준 금액은 데이터 속성으로 전달하므로 추가 API 호출은 없다. 정산 수정·업로드·잡이익 변경 후 기존 사용자 캐시 무효화가 그대로 적용된다.

## 검증 결과

- 변경 전 전체 Python 테스트: 102 통과, 5 건너뜀, 1 실패.
- 변경 후 전체 Python 테스트: 116 통과, 5 건너뜀, 같은 기존 실패 1개.
- 기존 실패: `test_ci_smoke_exercises_default_worker_count_instead_of_masking_it`. 저장소에 CI 설정 파일이 없어 발생한다. 이번 범위에서 CI 설정은 변경하지 않았다.
- 새 Python 테스트 14개: 영업일수 효과, 0원 영업일, 동기간 비교, 미래 수익 제외, 누락일·휴무 설정·일별 차액 처리, 월말 경계, CSV, 저장 후 갱신, 조회 수, 과거 월의 조회 범위 및 날짜 인덱스 검증.
- Node 목표 계산 테스트 5개 통과: 하루 목표 올림, 누락 보류, 남은 영업일 0, 목표 달성, 잘못된 금액.
- Python 컴파일, JS 구문 검사, git diff 공백 검사 통과.

합성 일별 기록 993일과 일회용 SQLite DB로 실제 운영 확장(일별 장부·캐시 락 포함)을 설치해 로컬 비교했다. 준비된 대시보드 요청의 SELECT 수는 변경 전후 모두 3회였다. 여러 측정에서 응답 중앙값은 변경 전 3.642~4.904ms, 변경 후 4.264~4.961ms였다. 서버 상태에 따른 측정 편차가 있어 속도 개선이나 완전한 무부하를 주장하지 않는다. 마지막 응답 본문은 39,850바이트에서 45,524바이트로 증가했다.

실제 Render·Neon의 지연시간, 최초 접속과 실제 PostgreSQL 연동은 이 작업에서 검증하지 않았다. PostgreSQL 실연동 테스트 5개는 테스트 접속 정보가 없어 건너뛰었다. 실제 약국 장부나 운영 DB에는 접근하지 않았다.
